# 研究规范：信源、搜索与验证

## 信源分级

| 等级 | 类型 | 使用规则 |
|---|---|---|
| T1 一手 | 官方文档/白皮书、论文、原始数据、法律与标准文本、当事机构或当事人的直接发布（官方博客、源码、财报、会议记录等） | 可单独支撑关键论断 |
| T2 权威二手 | 权威机构研究报告、知名专业团队博客、权威教材、高质量专业媒体 | 关键论断需再有一个独立 T1/T2 佐证 |
| T3 社区 | 论坛问答、个人博客、自媒体、百科 | 只作线索和补充视角，不可单独支撑关键论断 |

"独立"= 不同主体、不同出处。同一篇文章被多处转贴不算多个信源。

## 搜索策略

1. 关键词语言按领域选择：科技/学术领域优先英文检索（覆盖更全、更接近一手），历史/政策/本地实务类话题以中文检索为主，两边互补
2. 直达一手来源：先找该领域权威机构或当事方的官网/官方发布渠道，用 WebFetch 直接读，再用泛搜索补充
3. 涉及具体产品/版本：搜 changelog、release notes、官方定价/配额页
4. 有争议的机制问题：找维护者本人的说法（GitHub issue、官方论坛、作者博客）
5. **强制搜反方**：每个主题必搜批评、局限、失败案例、社区吐槽（GitHub issues、Hacker News、Reddit）——一面倒=没研究完；反方材料同时喂养文章的"常见误区"
6. **后继探测**：对版本化实体（产品/模型/API/框架）搜 "X latest version + 当前年月"，确认研究的是当前版本的行为；命名有规律时合并探针："X latest OR <下一版本号> release YYYY年M月"
7. 时间约束写法：查询词带"YYYY年M月"（或等价时间锚），禁止用裸年份作唯一时间约束
8. 留意搜索结果发布日期：过时信息（如已废弃的 API 行为）比没有信息更糟

**摘要 ≠ 证据**：搜索结果摘要只用于探索定向；支撑论断的摘录必须来自打开过的原文，并记录出处位置。

## 时效分级（核验窗口）

超窗内容视为待验证，重新核验后才能进笔记：

| 领域 | 核验窗口 |
|---|---|
| AI/大模型、区块链 | 3-6 个月 |
| 云服务、前端框架 | 6-12 个月 |
| 编程语言、数据库 | 1-2 年 |
| 算法原理、设计模式、数学 | 不限 |

## 适用对象（泛化防护）

- 机制表述标注适用对象：哪家产品 × 哪个版本 × 哪档套餐/部署方式
- 不同对象行为不同时，禁止合并成一句泛化陈述
- 区分三层并如实标注：官方文档声明 / 实测与社区报告 / 推测——"文档说"≠"实际是"；两者冲突时并列记录，不擅自裁决

## 时效标注

- 版本敏感内容（行为、数字、版本号、配额）必须标注"截至 YYYY-MM-DD"
- 训练记忆里的机制描述一律视为待验证假设
- 文档说法与训练记忆冲突时，以文档为准，并留意是否为近期变更

## 存疑标注（三档）

| 情形 | 表述方式 |
|---|---|
| 有来源 | 直接陈述，来源记入笔记 |
| 无来源但可严格推理 | "推断：……（依据是……）" |
| 无来源且无法推理 | "未查到官方说明"——宁缺毋滥 |

禁止：把推断写成事实；用"一般来说""通常"掩盖无依据。
